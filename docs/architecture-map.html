3Service Provider Architecture — Binding & Migration

An Organization (tenant) binds to an active Main Portal or Sub-Portal as its provider. Migration moves a tenant from a source provider to a destination.

Binding
EntityRole
Main Portaltop-level provider
Sub-Portaldelegated provider
Organizationtenant (consumer)

Table customer_tenants: organization_id ↔ provider_id

Migration flow

1preview: build manifest, compute SHA-256 fingerprint, set can_execute
2execute: require operation_id+fingerprint+actor match (else 409)
3update customer_tenants.provider_id, audit service_provider.migrated

Guards: credential setup policy must not change (before == after) · structure/ownership valid · idempotent retry · append-only service_provider_migrations

5Ownership — Legal Registry (not Authorization)

Key principle: an ownership holder is not a user account and grants no permission. Ownership records the legal owner of a business; sign-in/authorization flows through a separate permission system (portal_grants / customer_permissions).

Schema
TableColumns
ownership_holdersid, name no email/user link

Unique (owner_id, business_id) — no duplicate owner per business.

Rules
Created only at install (Main Portal) or business create Distributor/Shop: inherit parent owner set exactly Child owner set must equal parent owner set owner_ids max:30, distinct, must exist Immutable — no UPDATE/DELETE, no transfer endpoint Lifecycle stores owner_ids in snapshot (restore only) Migration re-validates ownership consistency
Consistency check

GET /businesses/{org}/ownership-check → compares org owner set vs each Shop/Distributor; returns {consistent, business_ids}. Detects drift only — no correction.

Known gap

Ownership is create-only. No governed flow exists to transfer, add/remove, or correct an owner after creation (e.g. sale, inheritance). See gap proposal.
