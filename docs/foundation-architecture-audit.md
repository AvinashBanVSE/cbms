## Corrections made during this review

- Distributor verification accepts the Shop Unique ID and its Shop-generated code in the Distributor workspace. Shop confirmation accepts the second code in the Shop workspace. The intended Distributor is still bound at issuance. Both verification stages retain permission checks, stage and expiry checks, revocation and atomic one-time use. Existing ID-based API routes retain their behavior.
- Organization creation checks the Service Provider's active operational state inside the creation transaction. A rejected provider assignment also rolls back any owner creation attempted in that request.
- The dashboard discovers authorized workspaces independently of service-catalogue access. An authenticated account can sign out even when it has no assignments. Each workspace API still enforces its operation's own authorization.
- Successful Organization setup verification consumes both the temporary password and the one-time code, where issued. Replaying the same proof cannot replace the existing restricted setup session.
- Main Portal can provision an account with explicit Organization onboarding authority and revoke that authority independently of the account lifecycle. Within an active Organization, this permission covers provisioning and setup-code reissue for its eligible Shop and Distributor user accounts. Main Portal retains the authority to provision Organization-level administrators and edit credential policy.
- A Main Portal administrator with the provider-user grant can provision, reissue setup codes for, and terminate Sub-Portal accounts. One-time email codes use the existing restricted setup and permanent password flow. The first provider permission is read access to the directory of Organizations currently served by that provider. Access follows the current tenant-provider assignment and termination invalidates existing sessions.
- Account recovery for active Sub-Portal and Organization users uses a temporary password sent only to the registered email address. Organization staff recovery requires an explicit root-level recovery grant and is limited to the same Organization. It excludes self-recovery and peer administrator recovery. Main Portal manages provider recovery and can revoke an Organization's staff recovery grant without changing account state.
- Account recovery checks the account's recent password history in the same transaction that changes its credential. Authorized Main Portal administrators can set the platform rule to 5–10 previous passwords through the Organization users workspace. The deployment setting `CBM_PASSWORD_HISTORY_COUNT` supplies the initial value and defaults to 5. Up to ten retired hashes are retained per user. Existing history starts with the first password changed under this feature.
- Signed-in users can enroll a TOTP authenticator after confirming their current password. Once enrolled, password sign-in also needs a current, unused authenticator code. Enrollment and removal invalidate other browser sessions. The MFA configuration currently applies per account.
- Main Portal operators with the legal-identity verification grant can attest that they reviewed evidence and associate the resulting legal identity with an existing business. A Shop or Distributor requires its own explicit association. Verification and association preserve professional identity, hierarchy and ownership.
- Main Portal can require authenticator enrollment for an individual Organization. An unenrolled user receives a time-limited enrollment session after password verification and must sign in with both factors after confirming enrollment. Other Organizations keep their own policies.
- The external verification adapter is ready to connect to an approved HTTPS registry. Deployments supply `CBM_LEGAL_VERIFIER_URL` and `CBM_LEGAL_VERIFIER_TOKEN`. The endpoint accepts JSON with `legal_name` and `evidence_reference`. It must return a JSON boolean `verified` and echo both fields for a confirmed match. The application records external provenance only for a matching successful response. Deployments that enable this integration need an approved registry endpoint, credentials, and a live integration check. Sections 3 and 5 require verified, explicit identity associations. Authorized evidence review satisfies the foundation identity workflow with the registry integration unconfigured.

- Authenticator replacement requires the existing Main Portal grant for the account context and an explicit identity-verification attestation. It revokes the previous authenticator and sessions, uses only the registered email for the temporary password, and requires a new password and a new authenticator before sign-in. A delegated Organization password-recovery grant does not include authenticator replacement.
- Authorized Main Portal administrators can set the validity of newly issued or reissued account setup OTPs to 1–15 minutes. The default is five minutes. Changes are audited, and previously issued codes retain their original deadline. This policy applies to Organization and Sub-Portal setup OTPs. Three failed proofs block account setup verification for a full hour from the third failure, even if a code is reissued.
- The Main Portal business directory counts each Organization's direct Shops and Distributors across lifecycle states and displays the resulting Distribution, Retail, or Hybrid Network. An Organization can be registered before its first Shop or Distributor. The configuration is calculated from the structure and has no effect on ownership, affiliation, or authorization.

## Engineering references

- Authorization is checked per request against the action, resource and verified tenant context. [OWASP Authorization Patterns](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Patterns_Cheat_Sheet.html)
- Tenant audit events carry verified tenant and actor context. Cross-tenant audit access requires explicit platform authority. [OWASP Multi Tenant Security](https://cheatsheetseries.owasp.org/cheatsheets/Multi_Tenant_Security_Cheat_Sheet.html)
- Verify transactional locking and retries on the deployment database. [Laravel 13 Query Builder](https://laravel.com/framework/docs/13.x/queries#pessimistic-locking)
- Recovery proofs are single-use with an expiry, and password changes use restricted sessions. [OWASP Forgot Password guidance](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html)

- TOTP interoperability and single-use validation follow [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238).
